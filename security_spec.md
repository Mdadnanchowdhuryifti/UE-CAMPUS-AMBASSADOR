# Security Specification — Ulterior Engineering CA Portal

## 1. Data Invariants
1. **Tier 0A (Main Developer Root — Strictly 2 Emails)**: ONLY `adnanchowdhury477@gmail.com` and `mdadnanchowdhuryifti@gmail.com` (with `email_verified == true`) hold Main Developer Root status. ONLY these two Main Developers can add, modify, or revoke `role == 'developer'` records in `/role_assignments/{emailKey}`, and neither Main Developer email record can be demoted or deleted.
2. **Tier 0B (Added Developer — Provisioned by Main Developers)**: A secondary Developer added by one of the two Main Developers (`role == 'developer'`) holds full operational control plus the ability to appoint/revoke Program Chair (`chair`) and Company CEO (`ceo`), but is strictly forbidden from adding, editing, or revoking `developer` assignments or touching Main Developer email keys.
3. **Role Assignment Email-to-Key Integrity**: Every create or update on `/role_assignments/{emailKey}` MUST satisfy `emailKey == emailToKey(incoming().email)`, guaranteeing document keys can never diverge from the stored email address.
4. **Tier 1 (Program Chair & Company CEO — Executive Parity)**: Both `chair` and `ceo` roles (appointed exclusively by Developers) hold identical full operational access across Chair Master, Recruitment Open/Close toggles, Secretary Hub, Leads 1–5, CA Portal, KPI weights, certificates, workshops, and subordinate role management (`secretary`, `lead1`–`lead5`, `ca`). Neither Chair nor CEO can enter Developer Mode or create/modify/delete `developer`, `chair`, or `ceo` assignments, nor alter `chairName`/`ceoName` directly.
5. **Granular Recruitment Closure Enforcement**: `/settings/program.recruitmentStatus` stores 7 booleans (`secretary`, `lead1`, `lead2`, `lead3`, `lead4`, `lead5`, `ca`) toggleable by Developers, Program Chair, and Company CEO. Creating a new document in `/applications/{applicationId}` MUST validate that `role` is one of the 7 official recruitment positions AND that its corresponding `recruitmentStatus` boolean is `true`.
6. **Atomic One-Per-User Workshop Registration & Seat Cap**: `/workshop_registrations/{regId}` MUST use deterministic key `{workshopId}_{uid}`, match `request.auth.token.email`, and verify `workshop.regs < workshop.seats`. Public updates to `/workshops/{workshopId}` can ONLY increment `regs` by `+1` up to `existing().seats` in the same atomic batch that creates `/workshop_registrations/{workshopId}_{uid}` (via `!exists(...)` and `existsAfter(...)`).
7. **Proof Submission Gating & Single-Metric Approval Bounds**: Non-assigned users may ONLY create `'Workshop Reg'` submissions using key `wsref_{workshopId}_{uid}` atomically paired with their new workshop registration (`!exists` + `existsAfter`). `'Tech Lead'` and `'Brand Post'` proof submissions strictly require `isAnyAssignedMember()`. Secretary and Squad Leads updating `/ambassadors/{ambassadorId}` during approval may increment at most ONE metric counter by `+1` per write.
8. **Strict Lead Segment, PII Isolation & Immutable Audit Fields**: Leads 1–5 remain strictly isolated to their portfolio and squad; PII collections remain owner-or-reviewer-scoped; public collections (`ambassadors`, `workshops`, `certificates`, `settings`, `config`) contain zero PII; `submitterUid`, `applicantUid`, `registrarUid`, `createdByUid`, and `createdAt` are immutable; server timestamps equal `request.time`.
9. **Developer-Only System Controls (`config/system`) & Emergency Read-Only Lockdown**: ONLY verified Developers (`role == 'developer'` or Main Developers) can create or update `/config/system`. When `config/system.emergencyLockdown == true`, EVERY write (`create`, `update`, `delete`) by any non-developer (including Chair, CEO, Secretary, Leads, CAs, and applicants) across ALL collections is strictly denied by Firestore rules.
10. **User Suspension & Ban Enforcement (`user_moderation/{emailKey}`)**: ONLY verified Developers can create, update, or delete `/user_moderation/{emailKey}` records, and Main Developer email keys can NEVER be suspended or banned (and secondary Developers cannot suspend/ban other Developers). Any non-main-developer whose `/user_moderation/{normalizedEmailKey()}.status` is `'suspended'` or `'banned'` is immediately denied all Firestore writes and signed out by the client.
11. **Immutable Developer Audit Trail (`audit_logs/{logId}`)**: ONLY verified Developers can read or append to `/audit_logs/{logId}`. `actorUid` and `actorEmail` must match `request.auth`, `createdAt == request.time`, and `update`/`delete` are unconditionally forbidden (`allow update, delete: if false`).
12. **Developer-Only Error Log Visibility (`error_logs/{errorId}`)**: ONLY verified Developers can `get`, `list`, `update` (`resolved` flag only), or `delete` `/error_logs/{errorId}`. Signed-in, non-blocked users (when not in lockdown) may create error records strictly matching their own `uid`/`email` with `resolved == false`.

## 2. The "Dirty Dozen" Adversarial Payloads (Must Return PERMISSION_DENIED)
1. **Secondary Developer Privilege Escalation**: A Developer-added secondary Developer attempts to add a new `'developer'` in `/role_assignments/newdev_at_gmail_dot_com` or suspend/ban a Main Developer in `/user_moderation/adnanchowdhury477_at_gmail_dot_com`.
2. **Main Developer Account Sabotage**: Any actor attempts to delete or demote `/role_assignments/adnanchowdhury477_at_gmail_dot_com` or `/role_assignments/mdadnanchowdhuryifti_at_gmail_dot_com`.
3. **Role Assignment Email-Key Mismatch**: Chair/CEO or Developer writes `/role_assignments/alice_at_gmail_dot_com` with `{ "email": "bob@gmail.com" }`, or writes `/user_moderation/alice_at_gmail_dot_com` with `{ "email": "bob@gmail.com" }`.
4. **Chair or CEO Accessing Developer `/admin` Controls**: Appointed `chair` or `ceo` attempts to update `/config/system` (`maintenanceMode: true`), list `/audit_logs`, list `/error_logs`, or create `/user_moderation/{emailKey}`.
5. **Emergency Lockdown Write Bypass**: While `/config/system.emergencyLockdown == true`, Program Chair, Lead, CA, or Applicant attempts to submit an application, register for a workshop, upload CSV roster rows, or update settings.
6. **Suspended or Banned User Write Bypass**: A user with `/user_moderation/{emailKey}.status == 'banned'` or `'suspended'` attempts to create a submission, workshop registration, club pitch, or application.
7. **Audit Log Tampering or Deletion**: Even a Main Developer attempts to `update` or `delete` an existing `/audit_logs/{logId}` document, or spoof `actorEmail` on create.
8. **Unverified Main Developer Email Spoofing**: Request with `email == "mdadnanchowdhuryifti@gmail.com"` and `email_verified == false` attempts to write `/config/system`, `/settings/program`, or `/role_assignments/{emailKey}`.
9. **Closed Role Application Bypass & Standalone Workshop Inflation**: Applicant submits `/applications/app_closed` when `recruitmentStatus` is false, or updates `/workshops/ws1` without atomic `/workshop_registrations/ws1_{uid}`.
10. **Ambassador Score Tampering & Cross-Squad Approval**: Secretary or Squad Lead attempts to jump `workshopRegs` by +500 or approve another squad's submission.
11. **Non-Developer Error Log Scraping or Spoofing**: Non-developer attempts to `list` `/error_logs`, or attempts to create an error log with `resolved: true` or another user's `userUid`.
12. **PII Scraping, Identity Spoofing & ID Poisoning**: General CA attempts `get` on another user's `/applications/{appId}` or `/user_moderation/{otherEmailKey}`, or writes `/config/evil$id`.
