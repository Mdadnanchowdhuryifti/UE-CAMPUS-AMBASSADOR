# Security Specification — Ulterior Engineering CA Portal

## 1. Data Invariants
1. **Tier 0A (Main Developer Root — Strictly 2 Emails)**: ONLY `adnanchowdhury477@gmail.com` and `mdadnanchowdhuryifti@gmail.com` (with `email_verified == true`) hold Main Developer Root status. ONLY these two Main Developers can add, modify, or revoke `role == 'developer'` records in `/role_assignments/{emailKey}`, and neither Main Developer email record can be demoted or deleted.
2. **Tier 0B (Added Developer — Provisioned by Main Developers)**: A secondary Developer added by one of the two Main Developers (`role == 'developer'`) holds full operational control plus the ability to appoint/revoke Program Chair (`chair`) and Company CEO (`ceo`), but is strictly forbidden from adding, editing, or revoking `developer` assignments or touching Main Developer email keys.
3. **Role Assignment Email-to-Key Integrity**: Every create or update on `/role_assignments/{emailKey}` MUST satisfy `emailKey == emailToKey(incoming().email)`, guaranteeing document keys can never diverge from the stored email address.
4. **Tier 1 (Program Chair & Company CEO — Executive Parity)**: Both `chair` and `ceo` roles (appointed exclusively by Developers) hold identical full operational access across Chair Master, Recruitment Open/Close toggles, Secretary Hub, Leads 1–5, CA Portal, KPI weights, certificates, workshops, and subordinate role management (`secretary`, `lead1`–`lead5`, `ca`). Neither Chair nor CEO can enter Developer Mode or create/modify/delete `developer`, `chair`, or `ceo` assignments, nor alter `chairName`/`ceoName` directly.
5. **Granular Recruitment Closure Enforcement**: `/settings/program.recruitmentStatus` stores 7 booleans (`secretary`, `lead1`, `lead2`, `lead3`, `lead4`, `lead5`, `ca`) toggleable by Developers, Program Chair, and Company CEO. Creating a new document in `/applications/{applicationId}` MUST validate that `role` is one of the 7 official recruitment positions AND that its corresponding `recruitmentStatus` boolean is `true`.
6. **Atomic One-Per-User Workshop Registration & Seat Cap**: `/workshop_registrations/{regId}` MUST use deterministic key `{workshopId}_{uid}`, match `request.auth.token.email`, and verify `workshop.regs < workshop.seats`. Public updates to `/workshops/{workshopId}` can ONLY increment `regs` by `+1` up to `existing().seats` in the same atomic batch that creates `/workshop_registrations/{workshopId}_{uid}` (via `!exists(...)` and `existsAfter(...)`).
7. **Proof Submission Gating & Single-Metric Approval Bounds**: Non-assigned users may ONLY create `'Workshop Reg'` submissions using key `wsref_{workshopId}_{uid}` atomically paired with their new workshop registration (`!exists` + `existsAfter`). `'Tech Lead'` and `'Brand Post'` proof submissions strictly require `isAnyAssignedMember()`. Secretary and Squad Leads updating `/ambassadors/{ambassadorId}` during approval may increment at most ONE metric counter by `+1` per write.
8. **Strict Lead Segment, PII Isolation & Immutable Audit Fields**: Leads 1–5 remain strictly isolated to their portfolio and squad; PII collections remain owner-or-reviewer-scoped; public collections (`ambassadors`, `workshops`, `certificates`, `settings`) contain zero PII; `submitterUid`, `applicantUid`, `registrarUid`, `createdByUid`, and `createdAt` are immutable; server timestamps equal `request.time`.

## 2. The "Dirty Dozen" Adversarial Payloads (Must Return PERMISSION_DENIED)
1. **Secondary Developer Privilege Escalation**: A Developer-added secondary Developer attempts to add a new `'developer'` in `/role_assignments/newdev_at_gmail_dot_com`.
2. **Main Developer Account Sabotage**: Any actor attempts to delete or demote `/role_assignments/adnanchowdhury477_at_gmail_dot_com` or `/role_assignments/mdadnanchowdhuryifti_at_gmail_dot_com`.
3. **Role Assignment Email-Key Mismatch**: Chair/CEO or Developer writes `/role_assignments/alice_at_gmail_dot_com` with `{ "email": "bob@gmail.com" }`.
4. **Chair or CEO Appointing Chair/CEO/Developer**: Appointed `chair` or `ceo` attempts to create `{ "role": "ceo" }`, `{ "role": "chair" }`, or `{ "role": "developer" }` in `/role_assignments/{emailKey}`.
5. **Closed Role Application Bypass**: Applicant submits `/applications/app_closed` with `{ "role": "Program Secretary" }` when `settings/program.recruitmentStatus.secretary == false`.
6. **Unverified Main Developer Email Spoofing**: Request with `email == "mdadnanchowdhuryifti@gmail.com"` and `email_verified == false` attempts to write `/settings/program` or `/role_assignments/{emailKey}`.
7. **Standalone Workshop Seat Inflation / Duplicate Registration**: Signed-in user attempts to update `/workshops/ws1` (`regs: existing + 1`) without creating a brand-new `/workshop_registrations/ws1_{uid}` in the same batch, or when `regs == seats`.
8. **Unassigned Outsider Spamming Tech Lead / Brand Post Submissions**: Unassigned Google user attempts to create `/submissions/sub_spam` with `{ "type": "Tech Lead" }` or standalone `{ "type": "Workshop Reg" }`.
9. **Ambassador Score Tampering by Secretary or Squad Lead**: Secretary or Squad Lead attempts to update `/ambassadors/ca1` setting `workshopRegs: existing + 500` or incrementing multiple metrics at once.
10. **Cross-Lead Segment Breach & Cross-Squad Approval**: `lead1` attempts to update `/tech_pipeline/UE-LEAD-2026-101`, or `lead2` attempts to approve a `Squad A` submission in `/submissions/sub_squad_a`.
11. **Shadow Field Injection & Privilege Tampering on Program Settings**: Chair/CEO attempts to overwrite `ceoName`/`chairName` or inject extra fields into `recruitmentStatus`, or Secretary attempts to toggle `recruitmentStatus`.
12. **PII Scraping, Identity Spoofing & ID Poisoning**: General CA attempts `get` on another user's `/applications/{appId}`, attacker submits spoofed `applicantUid`, or writes `/certificates/evil$id`.
